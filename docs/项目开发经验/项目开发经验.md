# 项目开发经验

## 多人提交需要本地与远程分层

Windows托管测试环境的临时目录可能使用短名称。同一目录通过resolve后会变成完整名称，测试应先规范化临时根路径再比较；不能为了消除字符串差异而放宽输出隔离检查。

暂存区可能与工作文件不同，应从Git对象检查；推送前还需逐个检查新增提交，删除最终文件不能移除历史中的大资产。规则与分享包清单职责不同，新增路径要先审核名单，再提交内容。

本地钩子不会随克隆自动启用，并且可能被绕过。远程策略应从目标分支读取受信任检查器，把候选代码仅当数据；普通候选测试在只读、无仓库秘密的独立任务执行。检查结果必须绑定实际候选SHA，不能只记到目标分支。

管理员权限不等于可以自审。启用管理员也受约束的主分支保护后，管理员本人发起的请求仍需另一位有权限成员审核；不能为完成自动化而擅自邀请账号或降低保护。

首次启用必需检查时，先让对应工作流在默认分支实际运行并核对检查名称，再绑定保护规则，避免要求一个从未上报的检查。配置读回通过后，还应使用正常工作分支和合并请求验证候选提交上的结果，不以管理员绕过代替验证。

只有一名代码所有者时，由其发起的关键规则修改无法自审。可由获准的新协作者先提出增加审核人的变更，现有管理员审核后再共同维护；账号邀请和审核人选择由用户决定，Agent不猜测名单。

## 通用工具与模型资产分开

工作目录可能包含几十GiB的母版、过程文件和备份，但通用工具只需文本源码。发布前先按白名单导出到干净仓库，不以删减原模型质量或删除证据来解决Git体积问题。

.gitignore只是一道防线，首次提交仍应核对具体文件。仓库导航必须只指向实际提供的实现，不能把原工作工程中未分发的案例脚本写成可用入口。

## 生成文档跨平台保持一致

HTML由Markdown和模板生成，提交后仍需逐字节一致。.gitattributes统一LF，避免Windows检出自动换行导致误报；从远程重新克隆后的检查比本机提交前检查更能说明实际交付状态。

## 证据分层

配置和模拟测试通过不等于模型视觉正确，推送成功也不等于所有外部软件已可用。实际场景、渲染器、Unity Skills和目标设备需在使用者环境中单独验证。

新增经验记录原因和适用范围，具体任务报告另存，不将私人路径、客户素材和临时授权写进公开仓库。发布规则见 [仓库发布与资产管理](../执行规范/仓库发布与资产管理.md)。
