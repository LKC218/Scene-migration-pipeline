# 多人协作与提交规范

## 一、团队约定

每人使用独立克隆和工作分支，不多人写同一个Git工作目录。模型、贴图、日志、输出、备份和个人配置保留在本地；禁止为了上传而删除需要的素材或证据。

仓库只接收获批的通用代码、文档、样例和测试。名单外文件默认阻塞，不悄悄跳过、不自动删除、不自动暂存。默认单文件不超过2MiB，禁止模型、压缩包、可执行文件、私人配置和缓存路径，改后缀也不能使二进制内容通过。

## 二、两份清单各管一件事

- configs/仓库提交白名单.json：完整Git仓库可包含的文件，包括钩子、工作流和协作工具。
- configs/分享白名单.json：给使用者打包的内容，是仓库允许内容的子集；不包含Git专用钩子和远程工作流。

不要把分享包白名单当作Git自动规则。检查器读取暂存区或Git提交对象，而不是只读磁盘工作文件。

新增路径分两次处理：先单独提出白名单扩展及理由，由维护者审核合并；获取新的main后，再提交新文件。不能在同一未审核分支中自行加白并上传新文件。现有文件的内容修改不需要扩展名单，但仍须检查和审核。

## 三、新成员准备

完整克隆后先获取远程main，再执行：

```powershell
git fetch origin main
python -X utf8 -B scripts/协作/初始化协作环境.py install
python -X utf8 -B scripts/协作/初始化协作环境.py check
```

由Agent协助完成，美术人员不必手动输入命令。初始化只修改当前克隆的Git配置，绑定当前Python和.githooks；不覆盖其他钩子，不改全局设置。换Python环境后重新核对安装。已有钩子或文件不一致时先人工整合，不强制替换。

钩子不会因克隆仓库自动安装，每位成员都必须完成此步骤。下载ZIP不具备Git协作环境，不能用它证明已安装防护。

## 四、日常提交与推送

1. 从最新main创建工作分支，只暂存本任务需要的文件，不使用强制添加。
2. pre-commit检查完整暂存树：已批准文件范围、文件类型、大小、有限敏感模式、源码语法、分享引用与HTML生成一致性。已删除的误跟踪文件不要求重新加入名单。
3. pre-push检查待发送的每个新增提交，防止先提交大文件再删除仍带入历史。拒绝直接推送main、非快进推送以及此入口未支持的标签和分支删除。
4. 推送前确认本机已获取最新origin/main。当前分支需包含该基线；远程检查还会按真实目标分支复核。
5. 提交合并请求，自动检查通过后由其他有权限成员审核；不得使用跳过检查、强制推送或降低规则来赶进度。

本地检查以已获取origin/main的批准白名单为准。检查失败只报告文件与原因，不打印疑似凭据原文，不清空暂存区、不改文件。

## 五、主分支和管理员

main要求合并请求、至少一名其他成员审核、代码所有者审核、最新推送重新确认、必需状态检查及讨论解决；不允许强制推送、删除或管理员默认绕过。

管理员LKC218负责白名单、钩子、检查器、工作流和其他关键规则。管理员身份不允许自己审批自己的合并请求；管理员发起的变更也需要另一位合适的审核者。若目前只有管理员一人，必须先由管理员添加合适的协作者，不能由Agent擅自邀请账号或放开绕过。

关键规则变更还需要代码所有者审核。管理员自己发起此类变更时，另一名审核者必须已是代码所有者并具备相应权限。初次扩充审核人可由新增协作者提出CODEOWNERS变更，再由现有管理员审核；不要通过关闭保护解决无人可审的问题。

首次安装检查体系可以在尚无分支保护的基线上完成一次初始化提交，确认远程检查正常后启用保护；这不是后续直接推送main的常规例外。

## 六、自动检查的信任边界

远程repository-policy使用目标分支中的检查器和白名单，只读取候选Git对象，不执行候选代码；结果明确绑定候选提交。候选分支修改自身检查器或白名单不能让新的路径自行通过。

repository-tests在普通pull_request的只读、无仓库秘密的隔离任务中执行候选测试；不用于发布或权限操作。第三方Action固定到提交号，凭据不留在工作目录，关键工作流受CODEOWNERS保护。

本地钩子可以被有本机控制权的人绕过，不是防恶意攻击的绝对安全边界。远程检查主要防止进入main，不能撤回已推到其他分支的秘密。敏感模式扫描也不是完整的秘密识别器；个人文件仍须人工核查。具备仓库管理权限的人仍能调整保护设置，团队不得私自这样做。

## 七、发生误提交

未推送时修正提交内容，不删除需要的本地文件。已推送口令时先撤销或轮换口令，再由管理员安排历史处理；最新版本删除不等于历史中消失。历史改写、远程删除、权限和许可证变更需要单独明确授权。

规则、校验脚本和工作流本身的变更必须经过维护者审核，不允许关闭检查后以检查通过作为依据。处理某个模型不意味着可以改变团队发布边界。
